# Техническое задание
## Консольная игра Wordle на Java

**Версия:** 1.0  
**Тип приложения:** консольное Java-приложение  
**Назначение:** однопользовательская игра Wordle с автоматической системой подсказок  
**Интерфейс:** CLI / консоль

---

# 1. Назначение системы

Необходимо разработать консольное приложение Wordle на языке Java.

Приложение должно:

- загружать словарь русских слов из внешнего файла;
- выбирать случайное слово длиной пять букв;
- предоставлять пользователю шесть попыток для угадывания;
- проверять корректность пользовательского ввода;
- формировать результат сравнения введённого слова с загаданным;
- предоставлять автоматические подсказки;
- позволять пройти игру полностью с использованием автоматических подсказок;
- вести технический лог работы приложения;
- корректно обрабатывать пользовательские и системные ошибки;
- иметь модульную архитектуру, позволяющую тестировать игровую логику независимо от консоли.

Исходное описание определяет игру как работу со словарём пятибуквенных существительных и ограничивает количество попыток шестью.

---

# 2. Термины и определения

**Ответ** — слово, случайным образом выбранное программой из игрового словаря и скрытое от пользователя.

**Попытка / ход** — ввод пользователем корректного слова и его последующая проверка.

**Игровой словарь** — набор нормализованных пятибуквенных слов, доступных для использования в игре.

**Подсказка результата** — строка длиной пять символов, описывающая соответствие букв введённого слова ответу.

**Автоматическая подсказка** — слово, автоматически выбранное программой из текущего множества допустимых вариантов.

**Нормализация слова** — преобразование строки к форме, используемой игровой логикой:
- перевод в нижний регистр;
- замена `ё` на `е`.

**Системная ошибка** — ошибка инфраструктурного характера: отсутствие файла словаря, невозможность создать лог, ошибка чтения файла и аналогичные ситуации.

**Игровая ошибка** — ситуация, возникшая вследствие пользовательского ввода и допускающая продолжение игры.

# 3. Участники системы

## 3.1. Игрок

Игрок:

- запускает приложение;
- вводит предполагаемые слова;
- получает результаты проверки;
- может запросить автоматическую подсказку;
- продолжает игру до победы либо исчерпания попыток.

## 3.2. Система

Система:

- загружает и подготавливает словарь;
- выбирает ответ;
- контролирует состояние игры;
- валидирует пользовательский ввод;
- вычисляет результат сравнения;
- вычисляет допустимые варианты для подсказок;
- обрабатывает ошибки;
- ведёт технический лог.

# 4. Основные бизнес-правила

## BR-01. Длина слова

Все игровые слова должны состоять ровно из **5 букв**.

---

## BR-02. Источник слов

Для игры используется внешний текстовый словарь русских существительных.

Одна строка файла соответствует одному слову.

Файл должен читаться в кодировке UTF-8.

---

## BR-03. Нормализация слов

Перед использованием слово необходимо:

1. привести к нижнему регистру;
2. заменить `ё` на `е`.

Данное правило применяется:

- к словам из исходного словаря;
- к пользовательскому вводу.

---

## BR-04. Количество попыток

Игрок получает **6 попыток**.

Корректно введённое слово уменьшает количество попыток на одну.

Некорректный пользовательский ввод попытку не расходует.

---

## BR-05. Победа

Игрок побеждает, если нормализованное введённое слово полностью совпадает с ответом.

После победы игровой цикл завершается.

---

## BR-06. Поражение

Если после шестой корректной попытки ответ не угадан, игра завершается поражением.

---

## BR-07. Некорректное слово

Слово не считается игровым ходом, если оно:

- пустое, за исключением специального сценария запроса подсказки;
- имеет длину, отличную от пяти букв;
- содержит недопустимые символы;
- отсутствует в игровом словаре.

После ошибки приложение должно снова ожидать ввод пользователя.

Количество оставшихся попыток изменяться не должно.

---

# 5. Формат результата проверки слова

После корректного хода система должна сформировать строку длиной пять символов.

Каждый символ соответствует букве введённого слова на той же позиции.

Используются следующие обозначения:

| Символ | Значение |
|---|---|
| `+` | буква присутствует в ответе и находится на правильной позиции |
| `^` | буква присутствует в ответе, но находится на другой позиции |
| `-` | буква отсутствует в ответе |

Правила обозначений непосредственно заданы исходным заданием.

### Пример

Введено:

`гонец`

Ответ:

`герой`

Результат:

`+^-^-`

# 6. Функциональные требования

## FR-01. Запуск приложения

При запуске приложение должно:

1. создать технический лог;
2. создать компонент загрузки словаря;
3. загрузить словарь из файла;
4. сформировать игровой словарь;
5. создать новую игровую сессию;
6. выбрать ответ;
7. установить количество попыток равным шести;
8. перейти к игровому циклу.

---

# 7. Работа со словарём

## FR-02. Загрузка файла

Приложение должно загружать словарь из текстового файла.

Чтение должно выполняться с использованием:

- UTF-8;
- `FileReader`;
- `BufferedReader`;
- конструкции `try-with-resources`.

---

## FR-03. Чтение слов

Каждая строка файла должна рассматриваться как отдельное исходное слово.

---

## FR-04. Формирование игрового словаря

После чтения всего файла приложение должно:

1. нормализовать слова;
2. отобрать слова длиной пять букв;
3. сформировать отдельный игровой словарь.

Исходный файл может содержать слова различной длины и отсортирован по алфавиту, поэтому фильтрация должна производиться после его чтения.

---

## FR-05. Пустой словарь

Если после загрузки и фильтрации игровой словарь пуст, игра не должна запускаться.

Ситуация должна рассматриваться как системная ошибка и фиксироваться в техническом логе.

---

# 8. Создание игровой сессии

## FR-06. Выбор ответа

При создании новой игры система должна случайным образом выбрать одно слово из игрового словаря.

---

## FR-07. Исходное состояние

При создании игровой сессии:

- `attemptsLeft = 6`;
- состояние игры — активно;
- список предыдущих слов пуст;
- история результатов пуста;
- история автоматических подсказок пуста.

---

# 9. Пользовательский ввод

## FR-08. Получение команды

Во время игрового цикла система ожидает строку из стандартного потока ввода.

Работа с `System.in` и `System.out` должна осуществляться только главным классом приложения.

Игровые и вспомогательные классы не должны напрямую взаимодействовать с консолью.

---

## FR-09. Нормализация пользовательского ввода

Полученная строка должна быть нормализована по правилам BR-03.

---

## FR-10. Предварительная валидация

До поиска слова в словаре необходимо проверить:

- допустимый формат строки;
- количество букв;
- допустимость используемых символов.

Не требуется обращаться к словарю для заведомо некорректного значения.

---

## FR-11. Проверка существования слова

После общей валидации система должна проверить наличие слова в игровом словаре.

При отсутствии слова должна возникнуть специализированная игровая ошибка, например:

`WordNotFoundInDictionaryException`.

Ошибка должна быть преобразована главным игровым циклом в понятное пользователю сообщение.

---

# 10. Выполнение хода

## FR-12. Проверка совпадения с ответом

После получения корректного слова система должна проверить его на полное совпадение с ответом.

При полном совпадении:

- фиксируется победа;
- дальнейшие попытки не выполняются;
- игровой цикл завершается.

---

## FR-13. Уменьшение количества попыток

Если слово корректно и является игровым ходом, количество оставшихся попыток должно уменьшиться на единицу.

---

## FR-14. Вычисление результата

Для каждой позиции введённого слова система должна определить одно из состояний:

- точное совпадение;
- наличие буквы на другой позиции;
- отсутствие буквы.

Результат должен быть преобразован в строку `+`, `^`, `-`.

Для формирования строки рекомендуется использовать `StringBuilder`.

---

## FR-15. Вывод результата

После выполнения хода главный класс должен вывести пользователю:

1. введённое слово;
2. на следующей строке — результат проверки.

---

# 11. Автоматическая подсказка

Исходное задание предусматривает возможность нажать `Enter` вместо ввода слова и получить автоматически подобранный вариант. Алгоритм должен учитывать результаты предыдущих ходов.

## FR-16. Запрос подсказки

Пустая строка во время активной игры должна трактоваться как запрос автоматической подсказки.

Пустая строка не должна рассматриваться как ошибочное слово.

---

## FR-17. Первая подсказка

Если пользователь запрашивает подсказку до выполнения первого хода, система может выбрать любое слово игрового словаря.

---

## FR-18. Последующие подсказки

После совершения одного или нескольких ходов система должна выбирать подсказку только среди слов, совместимых с полученной ранее информацией.

---

## FR-19. Использование истории

Для поиска подходящих слов необходимо учитывать:

- ранее введённые слова;
- результаты их проверки;
- буквы, отсутствующие в ответе;
- буквы, которые должны присутствовать;
- известные позиции букв;
- известные неправильные позиции букв.

---

## FR-20. Фильтрация вариантов

При вычислении множества кандидатов система должна последовательно исключать слова:

1. содержащие заведомо неподходящие буквы;
2. не содержащие обязательные буквы;
3. не имеющие обязательных букв на известных позициях;
4. противоречащие ранее полученным результатам.

---

## FR-21. Сохранение ответа среди кандидатов

Алгоритм фильтрации не должен исключать фактический ответ из множества возможных слов.

Для любого корректного состояния игры должно выполняться:

`answer ∈ candidateWords`

---

## FR-22. Исключение повторных подсказок

Система не должна выдавать одно и то же слово как автоматическую подсказку повторно в рамках одной игровой сессии.

---

## FR-23. Автоматическое прохождение

Пользователь должен иметь возможность пройти полный игровой цикл, используя только пустой ввод.

То есть последовательные нажатия `Enter` должны приводить к:

1. получению слова-подсказки;
2. выполнению с ним игрового хода;
3. обновлению состояния;
4. вычислению следующего допустимого слова.

Целевое поведение из исходного задания — возможность компьютера самостоятельно пройти игру, реагируя только на нажатия `Enter`.

# 12. Состояние игры

## FR-24. Хранение состояния

Игровой класс должен хранить как минимум:

- ответ;
- количество оставшихся попыток;
- состояние игры;
- игровой словарь либо набор доступных вариантов;
- историю ходов;
- информацию, необходимую для вычисления следующих подсказок.

---

## FR-25. Возможные состояния

Рекомендуемая модель состояния:

```text
IN_PROGRESS
WON
LOST
```

---

## FR-26. Завершение игры

Игровой цикл должен завершаться только если:

```text
state == WON
```

или:

```text
state == LOST
```

# 13. Логирование

## FR-27. Лог-файл

Программа должна создавать отдельный лог-файл.

Для записи используется `PrintWriter`.

---

## FR-28. Назначение лога

В лог необходимо направлять техническую информацию, не предназначенную пользователю.

В частности:

- системные ошибки;
- исключения;
- диагностические сообщения;
- значения ключевых переменных;
- некорректные внутренние состояния.

В консоль не должны выводиться stack trace и другие технические детали. Требование отделить игровой интерфейс от технических сообщений явно присутствует в исходном описании.

---

## FR-29. Передача логгера

Созданный объект `PrintWriter` должен передаваться компонентам приложения, которым требуется журналирование.

---

## FR-30. Управление ресурсом

Лог-файл должен использоваться через `try-with-resources`.

---

# 14. Обработка ошибок

## FR-31. Категории ошибок

Исключения должны разделяться минимум на две группы.

### Игровые

Например:

```text
WordNotFoundInDictionaryException
InvalidWordLengthException
InvalidWordFormatException
```

Такие ошибки допускают продолжение игрового процесса.

### Системные

Например:

```text
DictionaryNotFoundException
EmptyDictionaryException
DictionaryReadException
LogCreationException
```

Такие ошибки могут препятствовать запуску или продолжению программы.

---

## FR-32. Сигнатуры методов

Специализированные игровые исключения должны явно указываться в сигнатурах методов, если они относятся к проверяемым исключениям.

---

## FR-33. Общий обработчик

Главный класс должен содержать верхнеуровневую обработку непредвиденных ошибок.

Допускается охватить основной метод запуска программы конструкцией:

```java
// try {
//     ...
// } catch (Exception e) {
//     ...
// }
```

с записью технической информации в лог.

---

## FR-34. Проверка инвариантов

Для состояний, которые согласно игровой модели не должны возникать, необходимо предусмотреть проверки.

Примеры:

```text
attemptsLeft < 0
candidateWords не содержит answer
активная игра без возможного ответа
```

При нарушении внутреннего инварианта должно возникать соответствующее непроверяемое исключение, например наследник `RuntimeException`.

Исходное задание отдельно требует контролировать состояние игры, предотвращать зацикливание и проверять невозможные внутренние ситуации.

# 16. Требования к коллекциям и алгоритмам

## NFR-01. Коллекции

Для хранения данных должны использоваться структуры, соответствующие выполняемым операциям.

Допускается применение:

```text
List
Set
Map
```

Выбор конкретной реализации должен учитывать:

- поиск;
- проверку уникальности;
- исключение повторных подсказок;
- скорость фильтрации.

## NFR-02. Производительность

Необходимо избегать заведомо избыточных повторных операций над полным словарём.

Вычислительная сложность особенно важна для:

- проверки наличия слова;
- фильтрации кандидатов;
- поиска вариантов подсказки.

---

## NFR-03. Декомпозиция

Каждый класс должен иметь ограниченную и понятную область ответственности.

Игровая логика не должна смешиваться с:

# 17. Основные пользовательские сценарии

## UC-01. Успешное угадывание

**Предусловия:**

- словарь успешно загружен;
- игровая сессия создана.

**Основной сценарий:**

1. Система выбирает ответ.
2. Система ожидает ввод.
3. Игрок вводит существующее пятибуквенное слово.
4. Система валидирует слово.
5. Система уменьшает количество попыток.
6. Система сравнивает слово с ответом.
7. Система выводит результат.
8. Шаги 2–7 повторяются.
9. Игрок вводит правильный ответ.
10. Игра переходит в состояние `WON`.
11. Игровой цикл завершается.

---

## UC-02. Некорректное слово

1. Пользователь вводит слово.
2. Система определяет нарушение правил.
3. Система сообщает об ошибке.
4. Количество попыток остаётся неизменным.
5. Система снова ожидает ввод.

---

## UC-03. Поражение

1. Игрок выполняет шесть корректных ходов.
2. Ни один из них не совпадает с ответом.
3. `attemptsLeft` становится равным `0`.
4. Игра переходит в состояние `LOST`.
5. Игровой цикл завершается.

---

## UC-04. Получение первой подсказки

1. Игра только началась.
2. Пользователь нажимает `Enter`.
3. Система выбирает слово из словаря.
4. Выбранное слово используется как ход.
5. Результат хода сохраняется.
6. Количество попыток уменьшается.

---

## UC-05. Получение следующей подсказки

1. Существует история предыдущих ходов.
2. Пользователь нажимает `Enter`.
3. Система вычисляет множество возможных ответов.
4. Система исключает противоречащие предыдущим результатам слова.
5. Система исключает ранее предложенные подсказки.
6. Система выбирает слово.
7. Слово используется как следующий ход.

# 20. Неопределённости исходных требований

Следующие правила исходное описание однозначно не определяет, поэтому перед промышленной реализацией их желательно согласовать.

## TBD-01. Повторяющиеся буквы

Не определён точный алгоритм Wordle для случаев, когда одна и та же буква встречается несколько раз.

Например:

```text
ответ: масса
ввод:  касса
```

Необходимо отдельно определить, сколько повторных букв должно получать `^`, а сколько `-`.

Рекомендуется использовать стандартный Wordle-подход:

1. сначала определить все `+`;
2. исключить использованные буквы ответа;
3. затем определить `^`;
4. оставшиеся позиции пометить `-`.

До согласования это является предлагаемым правилом, а не исходным требованием.

---

## TBD-02. Допустимый алфавит

Исходный текст указывает на необходимость отклонять, например, английские буквы, однако точное регулярное выражение не определено.

Предлагаемый вариант:

после чего выполняется нормализация.
